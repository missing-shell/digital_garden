# QoS 0 - 最低级别

QoS 0 是 MQTT 协议中最低的服务质量级别。它也称为“即发即忘”或“最多一次”交付。

在 QoS 0 中，发布者向代理发送消息，而无需任何确认或传送保证。发布者不会存储和重新传输该消息。 

消息发布后，代理将立即将其分发给该主题的所有当前订阅者。但是，代理不会跟踪订阅者是否成功接收到消息。如果订阅者当前未连接或者由于任何原因错过了消息，则它将不会收到该消息。

QoS 0 提供最低的开销和延迟，因为不需要确认或重传。它适用于**偶尔消息丢失或重复可以接受的应用程序。**

以下是 QoS 0 的一些关键特征：

1. **消息丢失：**如果订阅者在发布消息时未连接，则它将不会收到该特定消息。QoS 0 中不会重传消息，因此消息一旦发布，就被视为已送达。
2. **无确认**：当 MQTT 代理成功传递或接收消息时，发布者不会收到来自代理或订阅者的任何确认。
3. **最低开销**：QoS 0 的开销最少，因为它不涉及用于确认或重传的额外消息交换。
4. **快速传递**：以 QoS 0 发布的消息会立即传递给当前连接到该主题的订阅者。

虽然与较高 QoS 级别（QoS 1 和 QoS 2）相比，QoS 0 提供的可靠性最低，但在可以容忍消息丢失或重复而不会产生重大影响的情况下，它仍然很有用。它通常用于实时数据更新比保证交付更重要的应用程序，例如传感器数据收集或实时流应用程序。

# QoS 1 - 默认级别

与 QoS 0 相比，QoS 1 提供更高级别的可靠性和保证。 

MQTT 中的 QoS 级别 1 可保证消息至少传送一次至接收者。发送方（发布客户端）存储消息，直到收到来自 MQTT 代理的 PUBACK（发布确认）数据包，该数据包确认收到消息。如果发送方在一定时间内没有收到PUBACK，它将重传消息以确保其送达。

当 MQTT 代理收到 QoS 1 的消息时，它会将该消息转发给所有订阅客户端，并向发送者响应 PUBACK 数据包。此 PUBACK 数据包用作对发送方的确认，确认消息已被代理成功接收。

由于 QoS 1 中的重传，消息可能会被多次发送或传递。如果发送方在特定时间范围内未收到 PUBACK 确认，则可能会发生这种情况。MQTT 代理确保消息至少传送到订阅客户端一次，但如果发生重传，客户端可能会收到重复的消息。

以下是 QoS 1 的主要特征：

1. **至少一次传递**：当消息以 QoS 1 发布时，MQTT 代理确保它至少传递给订阅客户端一次。代理确认从发布客户端收到消息并存储它，直到它可以成功传递给订阅者。
2. **消息确认**：代理收到以 QoS 1 发布的消息后，立即将该消息转发给所有订阅客户端，然后向发布客户端发送确认（PUBACK）。此确认通知发布客户端代理已成功接收并处理该消息。
3. **可能的消息重复**：在 QoS 1 中，由于重传尝试，可能会出现消息重复。如果代理在一定时间内没有收到订阅者的确认，它将重传消息以确保传递。结果，订户可能会收到消息的重复副本。
4. **无顺序保证：**虽然 QoS 1 确保至少一次传送，但它不保证消息到达的顺序。如果以 QoS 1 发布多个消息，则由于网络条件的变化或消息处理延迟，这些消息可能会无序地传递给订阅者。

QoS 1 在可靠性和效率之间取得了平衡。它保证消息被传递给订阅者，但不保证恰好一次传递或严格排序。它适用于**可以容忍偶尔重复消息或乱序传递的**场景，但可靠性仍然很重要。

# QoS 2 - 最高级别 

QoS 2 是 MQTT 协议中最高级别的可靠性和保证。它在发布客户端和订阅客户端之间提供端到端、一次性、 严格排序的 消息传递。

以下是 QoS 2 的主要特征：

1. **恰好一次传送**：QoS 2 保证消息恰好传送到订阅客户端一次。MQTT 代理确保消息被订阅者接收并确认，并采取必要措施防止重复。
2. **严格排序**：QoS 2 确保消息的严格排序。如果使用 QoS 2 发布多条消息，代理和订阅者将保证消息到达的正确顺序，并保留消息发布的顺序。
3. **无消息丢失或重复**：QoS 2 保证无消息丢失或重复。代理保留并跟踪消息交换的状态，以确保消息仅传递给订阅者一次。

QoS 2 是 QoS 级别中最可靠但也是资源最密集的选项。它涉及多个消息交换，并且需要额外的开销来跟踪状态并确保一次性传递。因此，它通常用于**消息完整性和可靠性至关重要的场景，例如金融交易、关键系统更新或消息重复或丢失不可接受的情况。**

从技术上讲，QoS 2 采用四步消息交换过程，涉​​及发布客户端、MQTT 代理和订阅客户端。让我们详细看看每个步骤：

1. **发布**：

    - 发布客户端将消息发送到 QoS 2 的 MQTT 代理。
2. **Pubrec（已收到发布）**：

    - 代理向发布客户端发送一个 Pubrec 数据包作为确认。
    - Pubrec 数据包确认代理已收到消息，并表明代理已准备好继续进行传递过程。
    - 如果发布客户端在特定时间范围内没有收到 Pubrec 数据包，则会将消息重新传输到代理。
3. **Pubrel（发布版本）：**

    - 订阅客户端收到来自代理的消息后，发送 Pubrel 数据包。
4. **Pubcomp（发布完成）：**

    - 代理通过发送 Pubcomp 数据包来确认消息已成功传递到订阅客户端。
    - Pubcomp 数据包充当发布客户端的完成消息，确认消息已成功传递。

通过利用这种强大的消息交换机制，QoS 2 可确保消息可靠地传送一次，从而保留消息的顺序并防止丢失和重复。

值得注意的是，与较低的 QoS 级别相比，实现 QoS 2 需要额外的网络开销、计算资源和增加的延迟。因此，当严格的消息完整性和可靠性至关重要，并且对于给定的应用程序要求来说，对性能的潜在影响是可以接受的时，应该使用它。
